# MsgPack performance (survey of October 2026)

This note says what the benchmarks measure, how `MsgPack` compares with other libraries on arm64 and x86-64,
where the time goes, and what the fast paths keep identical. The numbers are medians of nine repetitions of
at least 25 ms, in nanoseconds per call.

## What is measured

Two programs run the same operations on the same four documents, and `benchmarks/compare.py` joins their
output.

| program | libraries |
|---|---|
| `msgpack_benchmark` (`benchmarks/pack_unpack.cc`) | `MsgPack`, and the msgpack-c 1.3.0 that it bundles (`msgpack-c1.3` in the tables) |
| `msgpack_compare` (`benchmarks/compare.cc`) | msgpack-c 9.0.0 (`msgpack-c9`), nlohmann::json 3.12.0, mpack 1.1.1, RapidJSON (the commit the library pins) |

The comparison libraries are fetched at those tags by the benchmark targets only (`-DMSGPACK_BUILD_BENCH=ON`).
msgpack-c's headers and the bundled ones use the same names, so the two live in separate programs.

The documents come from `benchmarks/corpus.h`, as MessagePack bytes and as the same document in JSON text:

| document | size | content |
|---|---|---|
| small | 63 B | a flat record with one nested map |
| med | 502 B | a typical record: 15 keys, nested maps and arrays, every scalar type |
| large | 104 KB | an array of 200 med-like records |
| wide | 8.9 KB | one map of 1,000 keys |

| operation | what it does |
|---|---|
| `read` | bytes to a value: `MsgPack::unserialise`, `msgpack::unpack`, `json::from_msgpack`, `mpack_tree_parse` |
| `read+walk` | `read`, then visit every node |
| `read+lookup3` | `read`, then three lookups (a nested key, a number, a key at the end) |
| `lookup3` | the three lookups in a value that is already read and, for `MsgPack`, filled |
| `write` | value to bytes: `MsgPack::serialise`, `msgpack::pack` into an `sbuffer`, `json::to_msgpack` |
| `copy` | a copy of the value |
| `update` | `read`, set one field, `write` |
| `merge` | `read`, `MsgPack::update()` with a two-entry map (one key replaced, one added), `write`; `msgpack_benchmark` only |
| `json-write` | value to JSON text: `MsgPack::to_string`, `json::dump`, `rapidjson::Writer` over a DOM |
| `json-read` | JSON text to a value: RapidJSON parse and then `MsgPack(Document)`, `json::parse`, RapidJSON parse |
| `hash` | `MsgPack::hash()` |

Every row ends with a checksum of the document the operation produced, and `compare.py` fails when two
libraries that read the same bytes disagree. Visiting a document sums the same recipe over every node in
every library.

## Run it

```sh
cmake -B build-bench -DCMAKE_BUILD_TYPE=Release -DMSGPACK_BUILD_BENCH=ON
cmake --build build-bench --target msgpack_benchmark msgpack_compare
./build-bench/msgpack_benchmark > ours.txt
./build-bench/msgpack_compare > compare.txt
python3 benchmarks/compare.py ours.txt compare.txt
```

Both programs take a document name and an operation substring (`msgpack_benchmark med read`), and
`BENCH_QUICK=1` shortens every row for a run that only checks that they work. `msgpack_alloc` (a CTest test)
counts allocations for `unserialise`, `hash()` and `to_string()`.

## Results

| machine | compiler | flags |
|---|---|---|
| Apple M4 Pro, arm64, macOS 26 | Apple clang 17.0.0 | CMake Release: `-O3 -DNDEBUG`, C++20 |
| Intel Core i9-9980HK, x86-64, macOS 15 | Apple clang 17.0.0 | CMake Release: `-O3 -DNDEBUG`, C++20 |

Each machine ran both programs twice with nothing else running, and a cell is the smaller of the two medians. The `read` A/A (the same measurement taken twice in one run) is within 2% of 1 on the M4 Pro and within
10% on the i9.

Each cell is `MsgPack` in ns, then the fastest other library in that row, its time and the ratio of the two.
A ratio above 1 means `MsgPack` takes longer. `mpack` parses into a tree that points into the input and copies
no string, which makes it the floor for `read`.

## Where the time goes

**`read`.** `MsgPack::unserialise` unpacks into the value's own zone, so a read costs what `msgpack::unpack`
costs in the bundled msgpack-c plus a few allocations: 1.0 to 1.24x on arm64 and 1.0 to 1.32x on x86-64. msgpack-c
9.0.0 is no faster than 1.3.0 on the small document and up to 1.12x faster on the others on arm64; on x86-64 the two
are within 6%. The `msgpack_alloc` test counts 5 allocations for a read of its 0.5 KB record, and none for `hash()`
of it. mpack reads 1.7 to 3.4 times faster than `MsgPack` because it borrows the input.

**`read+walk` and `read+lookup3`.** These are the largest gaps: 5.9 to 10.2 times mpack on arm64 and 11.4 to 20.9
times on x86-64, except `read+lookup3` of the large document, which fills only the maps on its path (2.4x on both
machines). The first read or change of a map or array through the API fills it: a `Body` (a `shared_ptr` and its
control block) for every node, two for every map entry, and a hash-index entry per key. Visiting a value that is
already filled costs 2.0 to 3.5 times a visit of nlohmann's value on arm64 (3.0 to 4.4 on x86-64), because every
step of a map iterator looks the key up in the index.

**`lookup3`.** A lookup in a filled value is a hash lookup. It takes 33 to 64 ns on arm64 and 93 to 181 ns on x86-64,
1.1 to 1.4x RapidJSON's DOM on arm64 (1.7 to 2.1x on x86-64), which scans the keys of a map linearly: on the
1,000-key map `MsgPack` takes 0.27x nlohmann's time on arm64 (0.36x on x86-64) and is about 100 times faster than
RapidJSON.

**`write`.** `serialise` runs the msgpack-c packer into a buffer and copies the bytes into the returned
string. It takes 0.94 to 1.16x `msgpack::pack` into an `sbuffer` on arm64 and 1.05 to 1.30x on x86-64. The gap is
the fixed cost of the buffer and the copy, 17 ns on arm64 and 46 ns on x86-64 for the small document, which
matters only there. nlohmann's `to_msgpack` takes 2.2 to 2.7 times as long on arm64 and 4.0 to 5.3 times on
x86-64.

**`copy`.** A copy duplicates the tree into a new zone, as copying a msgpack-c `object` does: 1.0 to 1.13x its time
on arm64 on every document but the small one (1.58x), and 0.97 to 1.27x on x86-64 (small 2.02x). A copy of a
filled value costs the same as a copy of an unfilled one, because the index is not copied. A `shared_ptr` copy takes
4 ns on arm64 and 10 ns on x86-64, so a `MsgPack` copy is a deep copy and the documentation says so. nlohmann's
copy takes 2.2 to 7.1 times as long on arm64 and 2.6 to 8.3 times on x86-64.

**`update`.** Reading, setting one field and writing takes 0.18 to 0.60 of nlohmann's time on arm64 (0.11 to
0.84 on x86-64). Only the maps on the path to the field are filled.

**`json-write`.** `to_string` makes the calls on RapidJSON's `Writer` that a `Document` would make, straight
from the tree: 0.87 to 1.76x the time of the Writer over a prebuilt DOM on arm64 (1.06 to 1.25x on x86-64), where
the small and wide documents are the slow ones. nlohmann's `dump` takes 1.3 to 1.8 times as long on arm64 and 1.6
to 2.6 times on x86-64.

**`json-read`.** RapidJSON parses into a `Document` and the adaptor converts it: 1.3 to 1.6x the parse alone on
arm64 (1.7 to 1.8x on x86-64), and 1.4 to 5.3 times faster than nlohmann's parse on arm64 (1.6 to 4.8 on x86-64).

**`hash`.** `hash()` of a map root walks the msgpack tree and allocates nothing for a map of at most 16 keys
whose values pack to at most 256 bytes each (a bigger map allocates two arrays). An array root packs the whole
array, so its cost is close to `write`'s (large: 84,393 ns against 95,284 on arm64).

**Building a value.** Building the med record through the `MsgPack` API (`build`) takes 9,619 ns on arm64 and
32,336 ns on x86-64. Every `MsgPack` built from a scalar makes a zone of its own.

## What stays identical

The three fast paths change cost and nothing else. A change to one of them keeps these, and
`test/diff_test.cc`, `test/alloc_test.cc`, `test/lifetime_test.cc` and `tools/mutants.py` check them.

- **`unserialise`:** the value, the offset on return, every exception, the bytes of `serialise()`, the growth
  of a value after a change, and the lifetime of the value. The value never points into the input buffer,
  because strings, binaries and ext bodies are copied into the zone.
- **`hash()`:** the value, which is the XOR over each map's entries of `hash(key) ^ hash(value)` and the hash
  of the packed bytes of everything else. A map with a repeated key, or a key that is not a string, takes the
  filling path, which merges the repeats in the tree, and so does what `serialise()` and a copy give afterwards.
- **`to_string()`:** the text for every wire type (a binary is a string, an ext and an undefined are null),
  the indented form, the order of the keys and the escaping. The one difference from the earlier text is a
  `NaN` or `Inf`, which is `null` here and ended the text there. `as_document()` stays.
- **The layout of `Body`.** `msgpack.h` is a header, so a change to `Body`'s members changes the ABI of every
  consumer. A new constructor does not.

## Open

- **The `Body` per node.** The cost of `read+walk`, `read+lookup3` and a visit of a filled value is the lazy
  index. A per-size freelist for the `Body` blocks, tried as a prototype, gave 1.06 to 1.24x on arm64 and 1.4 to
  1.7x on x86-64 for a read followed by touching every node. It needs a decision on blocks freed by another
  thread (a bounded per-thread cache or a shared pool) and on the memory each thread retains. It is not in the
  library.
- **Building through the API.** Every scalar owns a zone chunk, so building a record scalar by scalar is
  dominated by allocation.
- **The JSON adaptor.** `json-read` pays 40 to 50% over the RapidJSON parse for the conversion.
